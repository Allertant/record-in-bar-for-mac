# Record in Bar 编辑页改造方案

## 1. 文档目的

这份文档只回答一个问题：

如何在 **状态栏弹层** 内，稳定实现下面 5 条同时成立的编辑页体验：

1. 详情页仍然在状态栏弹层里
2. 正文使用富文本编辑器
3. 正文随内容自然增高
4. 不使用编辑器内部滚动，只使用页面滚动
5. 保留 AI 总结卡片

本文档不直接修改代码，只形成后续实现方案。

## 2. 当前问题结论

当前实现已经验证过两条路线，都不满足目标：

### 2.1 `STTextView + 内部滚动`

优点：

- 稳定
- 富文本能力成熟
- 光标、换行、滚动体验整体可靠

缺点：

- 不满足“正文自然增高”
- 不满足“只使用页面滚动”

### 2.2 `STTextView + 自然增高`

这条路已经触发过两个根本问题：

1. `Invalid view geometry: width is infinity`
2. `The window has been marked as needing another Update Constraints in Window pass`

这不是简单参数问题，而是结构性冲突。

## 3. 资料结论

### 3.1 Apple 文档结论

根据 Apple AppKit 文档：

- `NSText` / `NSTextView` 提供了：
  - `isVerticallyResizable`
  - `isHorizontallyResizable`
  - `sizeToFit()`
  - `scrollRangeToVisible(_:)`
- `NSView` 提供了：
  - `intrinsicContentSize`
  - `invalidateIntrinsicContentSize()`

这些接口说明，**AppKit 原生文本系统本身支持“内容驱动尺寸”的文本视图**。

参考：

- `NSTextView` / `NSText`
  - https://developer.apple.com/documentation/appkit/nstextview
  - https://developer.apple.com/documentation/appkit/nstext
- `NSView.intrinsicContentSize`
  - https://developer.apple.com/documentation/appkit/nsview/intrinsiccontentsize
- `NSView.invalidateIntrinsicContentSize()`
  - https://developer.apple.com/documentation/appkit/nsview/invalidateintrinsiccontentsize%28%29

### 3.2 SwiftUI 文档结论

根据 SwiftUI 文档：

- `NSViewRepresentable.sizeThatFits` 是 SwiftUI 与 AppKit 之间的尺寸协商入口
- 但它不适合在协商过程中反向修改底层 AppKit 视图几何

否则很容易形成：

`SwiftUI 测量 -> AppKit 改 frame -> AppKit 重新约束 -> SwiftUI 再测量`

参考：

- `NSViewRepresentable.sizeThatFits`
  - https://developer.apple.com/documentation/swiftui/nsviewrepresentable

### 3.3 `STTextView` 源码结论

从当前已接入的 `STTextView` 源码可以确认：

- `STTextView` 自身继承自 `NSView`
- 它实现了 `intrinsicContentSize`
- 它内部观察 `textLayoutManager.usageBoundsForTextContainer`
- 当文本布局尺寸变化时，它会主动设置：
  - `needsUpdateConstraints = true`

这意味着：

`STTextView` 自身就是一个会主动驱动约束刷新的复杂控件。

在普通窗口中，这通常没问题；但在当前结构里：

- 外层是 `NSPopover`
- 中层是 `NSHostingController`
- 内层是 `SwiftUI ScrollView`
- 再内层是 `NSViewRepresentable`
- 最内层是 `STTextView`

一旦还要求“正文高度随内容变化”，就很容易形成约束与测量的循环。

所以结论非常明确：

**`STTextView` 适合做稳定的固定高度富文本编辑器，不适合在当前弹层结构里继续承担“自然增高正文”的核心控件。**

## 4. 组件选型结论

### 4.1 放弃 `STTextView` 作为详情页正文核心控件

保留它的唯一合理场景是：

- 固定高度
- 编辑器自己滚动

这不符合本次目标。

### 4.2 采用 `AppKit NSTextView` 作为正文核心控件

选择原因：

1. `NSTextView` 是 macOS 原生成熟富文本编辑器
2. 可以关闭内层滚动，仅作为可编辑文本视图存在
3. 可以通过 `sizeToFit()` 和 `intrinsicContentSize` 做“内容驱动高度”
4. 由我们自己控制高度刷新时机，避免 `STTextView` 那种内部额外约束观察链

## 5. 目标架构

### 5.1 顶层结构保持不变

- `AppDelegate`
- 状态栏按钮
- `NSPopover`
- `NSHostingController`
- `AppMenuRootView`

也就是说：

**首页仍然保留在当前状态栏弹层结构中。**

### 5.2 详情页改为“SwiftUI 壳 + AppKit 编辑内容”

详情页不再让 SwiftUI 负责正文编辑区的尺寸计算。

新的结构建议：

- `EditorPageView`
  - SwiftUI 只负责：
    - 顶部栏
    - 删除按钮
    - AI 分析按钮
    - AI 总结卡片
    - 外层页面 `ScrollView`
- 正文编辑区域改为一个 `NSViewControllerRepresentable`
  - 内部挂载一个 `EditorDocumentViewController`

### 5.3 `EditorDocumentViewController` 内部结构

建议完全使用 AppKit 组织正文编辑区：

- 外层：`NSScrollView`
  - 这是页面唯一滚动容器
- `documentView`：`NSStackView` 或自定义 `NSView`
  - 标题容器
  - 正文容器
  - AI 总结容器占位桥接区

重点：

- **标题编辑区**
  - 可继续使用 `NSTextField` 或轻量 `NSTextView`
  - 多行，自然高度
- **正文编辑区**
  - 使用 `NSTextView`
  - 不放入自己的 `NSScrollView`
  - `isVerticallyResizable = true`
  - `isHorizontallyResizable = false`
  - `textContainer.widthTracksTextView = true`
  - `textContainer.heightTracksTextView = false`

正文高度变化时：

- 重新计算正文容器高度
- 调整 `documentView` 布局
- 由外层页面 `NSScrollView` 负责整体滚动

## 6. 为什么这条路可行

### 6.1 滚动系统只保留一个

当前最容易出 bug 的点，就是：

- 编辑器自己要滚
- 页面也要滚

新的方案里：

- 只有页面外层 `NSScrollView` 滚动
- 正文 `NSTextView` 本身不带独立滚动容器

### 6.2 尺寸控制回到 AppKit 内部

当前最大问题，是 SwiftUI 参与了正文高度计算。

新的方案里：

- 高度变化完全在 AppKit 里消化
- SwiftUI 只看到一个稳定的“详情页内容块”

这样能避免：

- `width is infinity`
- `Update Constraints in Window pass`
- `sizeThatFits` 递归

### 6.3 AI 卡片仍然可以保留

AI 总结卡片不是本次问题根源，所以不需要删除。

它只需要从“正文编辑器尺寸链的一部分”变成：

- 正文之后的普通展示卡片
- 由外层页面统一排布

## 7. 具体改造步骤

### 第一步：冻结当前 `EditorPageView` 的交互边界

保留：

- 顶部操作栏
- 删除确认
- AI 分析按钮
- AI 总结卡片
- 复制按钮

暂停继续在当前 `STTextNoteEditor` 上做自然增高尝试。

### 第二步：引入新的 AppKit 编辑容器

新增组件建议：

- `EditorDocumentViewController.swift`
- `EditorDocumentContainerView.swift`
- `GrowingTitleTextView.swift`
- `GrowingNoteTextView.swift`

### 第三步：实现正文自然增高机制

正文区实现原则：

1. 文本变化后只在 AppKit 内部重算高度
2. 通过 `layoutManager.usedRect(for:)` 或 `fittingSize` 得到正文内容高度
3. 更新正文容器约束常量
4. 调用 `invalidateIntrinsicContentSize()` 仅通知上层容器
5. 不在 SwiftUI `sizeThatFits` 里修改底层 frame

### 第四步：外层页面统一滚动

外层页面只允许一个滚动容器：

- AppKit `NSScrollView`

如果详情页还需要保留 SwiftUI 外壳，则：

- SwiftUI 顶栏固定
- 正文与 AI 总结整体作为一个 AppKit 内容区

或者更进一步：

- 详情页整个主体都交给 AppKit
- SwiftUI 仅负责最外层承载

### 第五步：桥接数据与保存

编辑数据流建议：

- `EditorPageView` 仍持有：
  - `draftTitle`
  - `draftNote`
- AppKit 文本控件只通过 delegate 回调写回这两个 draft
- 保存策略保持当前的：
  - `300ms` 防抖
  - 页面离开时强制落库

## 8. 风险点

### 8.1 不是“小修”

这不是换一个组件名就能完成的任务，而是要：

- 重新设计详情页正文区域的技术边界
- 从 `SwiftUI 参与文本区尺寸协商`
- 改成 `AppKit 自主管理正文布局`

### 8.2 标题区也可能需要一起 AppKit 化

如果标题继续使用 SwiftUI `TextField(axis: .vertical)`，而正文改成 AppKit 自增长文本区，两个系统的排版与高度行为可能不一致。

更稳的方案是：

- 标题也使用 AppKit 文本组件
- 统一归到同一个文档视图里

### 8.3 状态栏弹层尺寸仍然有限

即使实现成功，`NSPopover` 本身仍然是小空间。

所以最终体验会是：

- 页面统一滚动
- 正文自然展开
- 但可视区域仍然有限

这是产品形态限制，不是技术 bug。

## 9. 推荐实施顺序

推荐按下面顺序做，而不是一次性硬改：

1. 先保留现有首页和 AI 卡片逻辑
2. 先只替换详情页正文区域为 AppKit 文档容器
3. 验证：
   - 多行输入
   - 回车换行
   - 光标跟随
   - 页面滚动
4. 稳定后，再决定标题区是否一并 AppKit 化
5. 最后再做视觉细化

## 10. 最终结论

要同时满足你最早的 5 条要求，正确路线不是继续折腾 `STTextView + SwiftUI sizeThatFits`，而是：

**保留当前状态栏主页和 AI 总结卡片，详情页正文区改为 AppKit 原生文档式编辑容器，核心富文本控件换成 `NSTextView`，并由单一外层滚动容器承接整个页面滚动。**

这是当前可行性最高、长期最稳的一条路线。
